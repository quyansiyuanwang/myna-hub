# Contributing to myna-hub

Contributions are pull requests against this repository. Every contribution goes into
the folder that matches its kind — `skills/`, `mcps/` or `plugins/`.

## Workflow

1. Fork the repository and create a branch.
2. Scaffold the entry (fills in the required fields and regenerates the index):
   ```sh
   npm run new -- skill my-skill --name 我的技能 --desc 什么时候用它 --tags utility
   npm run new -- mcp my-server --command npx --args "-y,@scope/server" --env API_KEY=
   npm run new -- plugin my-pack --skills my-skill --mcps my-server
   ```
   Writing files by hand works too; the scaffolding only exists so the shape is right.
3. Fill in the content (see the rules below).
4. Verify everything:
   ```sh
   npm run verify     # registry in sync + strict validation + inventory
   ```
5. Open a pull request. CI runs the same checks and fails on any inconsistency.

Removing an entry, including the reference cleanup in plugins that use it:

```sh
npm run remove -- skill my-skill          # refuses when a plugin still references it
npm run remove -- mcps my-server --force  # also strips the reference from plugins
```

## Local commands

| Command | What it does |
|---|---|
| `npm run check` | structural + quality validation (warnings do not fail) |
| `npm run check:strict` | same, warnings fail (what the weekly audit runs) |
| `npm run registry` | regenerate `registry.json` from the three folders |
| `npm run registry:check` | fail when `registry.json` is out of date |
| `npm run stats` | inventory: counts, tag spread, runtime split, prompt cost |
| `npm run stats:diff` | the same, plus what changed versus `origin/main` |
| `npm run audit` | probe every upstream package referenced by an MCP server |
| `npm run test` | self-test the validator itself (16 injected defects) |
| `npm run verify` | `registry:check` + `check:strict` + `stats` + `test` |

## Automation

| Workflow | Trigger | Purpose |
|---|---|---|
| `validate.yml` | every push / PR | validation on Node 20 and 22, validator self-test, registry drift, per-PR inventory and prompt-cost delta |
| `audit.yml` | weekly (Monday) | strict validation, upstream package availability, stats artifact, opens an issue on failure |

The weekly job exists because some failures cannot be caught at review time: an upstream
package gets unpublished, or accumulated warnings cross a threshold.

## Repository layout

```
skills/<id>/SKILL.md        instruction package
mcps/<id>/mcp.json          MCP server definition (+ README.md)
plugins/<id>/plugin.json    bundle referencing skills and MCP servers (+ README.md)
registry.json               index, regenerated by the validator
```

## Size and cost limits

`name` and `description` are injected into **every request** as part of Myna's skill list,
so they are a permanent token cost, not just documentation:

| Field | Recommended | Hard limit |
|---|---|---|
| `name` | ≤ 24 characters | 40 |
| `description` | ≤ 120 characters | 200 |
| `id` | ≤ 32 characters | 32 |
| tags | ≤ 4 | 6 |
| skill body | ≤ 6000 characters | 20000 |
| any file | — | 256 KB |

The description must answer "when would I use this", not "what is implemented inside".
A description longer than about 120 characters costs every user tokens on every message.

Tags come from a fixed vocabulary in `scripts/validate.mjs` (`KNOWN_TAGS`). Reuse an
existing tag when it fits; a new tag needs a line added there, which keeps search results
from fragmenting into near-duplicates.

## Naming rules

- Every `id` is the directory name and matches `[a-z0-9-]+` (lowercase, digits, hyphen).
- Ids are unique within their folder.
- Use the same id across kinds only when that is intentional and unambiguous.

## Adding a skill

Create `skills/<id>/SKILL.md`:

```markdown
---
name: 日报生成
description: 汇总今天的提醒与日程，生成一段日报文本
---
1. 调用 `get_datetime` 获取今天的日期与当前时间。
2. …
```

- `name` and `description` are required, non-empty, single line, in Simplified Chinese
  unless the skill is inherently English.
- The body is a sequence of concrete, imperative steps the model can follow.
- Reference Myna's tools by their exact names in backticks, for example
  `` `get_datetime` ``, `` `clipboard_read` ``, `` `run_applescript` ``.
- Keep the skill focused and under roughly 60 lines. Split unrelated behaviour into
  separate skills.
- Do not embed secrets, personal paths or user-specific data.

## Adding an MCP server

Create `mcps/<id>/mcp.json`:

```json
{
  "id": "filesystem",
  "name": "文件系统",
  "description": "读写指定目录下的文件（只读/读写取决于参数）",
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-filesystem", "~/Documents"],
  "env": {}
}
```

- `command` is required and is started through `/usr/bin/env`.
- `args` is an array of strings (may be empty); `env` is an object (may be empty).
- Prefer official or widely used servers. Verify the package actually resolves before
  submitting, for example `npm view @modelcontextprotocol/server-filesystem version`.
- Add `mcps/<id>/README.md` documenting prerequisites, what the server exposes, and
  which `args` the user should edit (paths, tokens, and so on). Never commit credentials.

## Adding a plugin

Create `plugins/<id>/plugin.json`:

```json
{
  "id": "morning-routine",
  "name": "早晨例程",
  "description": "组合早间简报与记忆图谱，生成简报并记录当天要点",
  "skills": ["morning-brief"],
  "mcps": ["memory"]
}
```

- Every id in `skills` and `mcps` must already exist in this repository.
- At least one of the two arrays must be non-empty.
- Add `plugins/<id>/README.md` describing what the combination does and how to use it.

## Registry rules

`registry.json` is generated, not hand-written:

```json
{
  "version": 1,
  "skills":  [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "skills/<id>" }],
  "mcps":    [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "mcps/<id>" }],
  "plugins": [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "plugins/<id>", "skills": [], "mcps": [] }]
}
```

Arrays are sorted by `id`. The validator fails if the registry and the folders disagree,
or if a name or description differs from the source file.

## What the validator checks

Beyond "does it parse", the validator enforces rules that prevent silent breakage:

- **Structure** — folder names match `[a-z0-9-]+`, required files exist, ids match the
  directory name, JSON parses, plugin references resolve.
- **Registry fidelity** — every entry matches the source file field for field, tags
  included; arrays are sorted; `registry.json` is byte-identical to what
  `--write-registry` would produce, so hand edits are caught in CI.
- **Prompt cost** — name/description lengths, punctuation, placeholder text
  (`待填写` / `TODO`) from scaffolding, duplicate descriptions across entries.
- **Portability** — MCP `command`, `args` and `env` must not contain machine-specific
  paths (`/Users/...`, `C:\...`); env keys must be `UPPER_SNAKE_CASE`; the registry
  `runtime` must match what the command implies.
- **Safety** — credential patterns (API keys, tokens, private key blocks) fail the build
  if they ever appear in a committed file.
- **Docs** — relative markdown links must resolve; long skill bodies should be sectioned;
  plugins should ship a README.
- **Hygiene** — no `.DS_Store`, no vendored `node_modules`, no build output, no symlinks,
  no file over 256 KB.
