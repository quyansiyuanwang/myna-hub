# Contributing to myna-hub

Contributions are pull requests against this repository. Every contribution goes into
the folder that matches its kind — `skills/`, `mcps/` or `plugins/`.

## Workflow

1. Fork the repository and create a branch.
2. Add your files under the matching folder (see the rules below).
3. Regenerate the index:
   ```sh
   node scripts/validate.mjs --write-registry
   ```
4. Validate:
   ```sh
   node scripts/validate.mjs
   ```
5. Open a pull request. CI runs the same validator and fails on any inconsistency.

## Repository layout

```
skills/<id>/SKILL.md        instruction package
mcps/<id>/mcp.json          MCP server definition (+ README.md)
plugins/<id>/plugin.json    bundle referencing skills and MCP servers (+ README.md)
registry.json               index, regenerated by the validator
```

## Naming rules

- Every `id` is the directory name and matches `[a-z0-9-]+` (lowercase, digits, hyphen).
- Ids are unique within their folder.
- Use the same id across kinds only when that is intentional and unambiguous.

## Adding a skill

Create `skills/<id>/SKILL.md`:

```markdown
---
name: 日报生成
description: 汇总今天的提醒与日程，生成一段日报文本
---
1. 调用 `get_datetime` 获取今天的日期与当前时间。
2. …
```

- `name` and `description` are required, non-empty, single line, in Simplified Chinese
  unless the skill is inherently English.
- The body is a sequence of concrete, imperative steps the model can follow.
- Reference Myna's tools by their exact names in backticks, for example
  `` `get_datetime` ``, `` `clipboard_read` ``, `` `run_applescript` ``.
- Keep the skill focused and under roughly 60 lines. Split unrelated behaviour into
  separate skills.
- Do not embed secrets, personal paths or user-specific data.

## Adding an MCP server

Create `mcps/<id>/mcp.json`:

```json
{
  "id": "filesystem",
  "name": "文件系统",
  "description": "读写指定目录下的文件（只读/读写取决于参数）",
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-filesystem", "~/Documents"],
  "env": {}
}
```

- `command` is required and is started through `/usr/bin/env`.
- `args` is an array of strings (may be empty); `env` is an object (may be empty).
- Prefer official or widely used servers. Verify the package actually resolves before
  submitting, for example `npm view @modelcontextprotocol/server-filesystem version`.
- Add `mcps/<id>/README.md` documenting prerequisites, what the server exposes, and
  which `args` the user should edit (paths, tokens, and so on). Never commit credentials.

## Adding a plugin

Create `plugins/<id>/plugin.json`:

```json
{
  "id": "morning-routine",
  "name": "早晨例程",
  "description": "组合早间简报与记忆图谱，生成简报并记录当天要点",
  "skills": ["morning-brief"],
  "mcps": ["memory"]
}
```

- Every id in `skills` and `mcps` must already exist in this repository.
- At least one of the two arrays must be non-empty.
- Add `plugins/<id>/README.md` describing what the combination does and how to use it.

## Registry rules

`registry.json` is generated, not hand-written:

```json
{
  "version": 1,
  "skills":  [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "skills/<id>" }],
  "mcps":    [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "mcps/<id>" }],
  "plugins": [{ "id": "...", "name": "...", "description": "...", "tags": [], "author": "...", "path": "plugins/<id>", "skills": [], "mcps": [] }]
}
```

Arrays are sorted by `id`. The validator fails if the registry and the folders disagree,
or if a name or description differs from the source file.

## Continuous integration

`.github/workflows/validate.yml` runs `node scripts/validate.mjs` on every push and pull
request. A pull request that leaves the registry out of sync will not pass.
